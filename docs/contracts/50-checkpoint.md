# قرارداد ۵ — checkpoint و وضعیت

نسخه: 0.1 · وابسته به: [00-invariants](00-invariants.md) (I4, I8, I9, I11)

سؤال این سند: «وضعیت معتبر» دقیقاً چیست، کجا زندگی می‌کند، چطور ساخته و ابطال می‌شود، و پس از
قطع ناگهانی چطور به آن برمی‌گردیم؟

---

## 1. دو انبار، یک حقیقت

| انبار | نقش | چه چیزی را تضمین می‌کند |
| --- | --- | --- |
| Git (شاخهٔ `csef/validated`) | **هویت** تغییرات معتبر | دقیقاً چه کدی تأیید شد |
| SQLite (`.csef/journal.db`) | **تاریخ** رخدادها | چه اتفاقی افتاد، چه چیزی تأیید شد، چه هزینه‌ای رفت |
| انبار شواهد | **مدرک** | چرا معتبر است |

هیچ‌کدام به‌تنهایی «وضعیت» نیست. وضعیت = سه‌گانهٔ (commit, journal, evidence bundle) که با hash
به هم گره خورده‌اند.

SQLite منبع وضعیت *عملیاتی* است (تراکنش، lease، بازیابی). فایل JSON فقط خروجی برای بازرسی و
diff است، نه منبع حقیقت. این تفکیک عمدی است: JSON برای آدم، SQLite برای ماشین.

## 2. ساختار checkpoint

```yaml
checkpoint_id: ck-0007
project_id: prj-alpha
parent: ck-0006                   # زنجیرهٔ خطی؛ هیچ‌گاه چند والد
commit: "git:sha..."              # روی شاخهٔ csef/validated
requirements_satisfied: [AUTH-001]
task_id: T-0042
evidence_bundle: eb-...
evidence_bundle_hash: "sha256:..."
policy_hash: "sha256:..."
baseline_hash: "sha256:..."
env_fingerprint: "sha256:..."
schema_version: 1
created_by: controller            # هر مقدار دیگر = checkpoint نامعتبر
created_at: "..."
verdict: PASS                     # فقط PASS پذیرفته می‌شود
```

قوانین:

- فقط **Controller** می‌سازد (I4). عامل و آداپترها دسترسی نوشتن به این رکورد ندارند.
- زنجیره **خطی** است. آزمایش‌ها در worktree جدا انجام می‌شوند و هرگز وارد شاخهٔ معتبر نمی‌شوند.
- هر checkpoint باید دست‌کم یک نیازمندی را کامل کند؛ checkpoint بدون نیازمندی، نویز است.

## 3. بازتولیدپذیری

```
csef verify ck-0007
```

باید بدون دخالت عامل: checkout تمیز commit، بازسازی محیط از روی `env_fingerprint`، اجرای مجدد
همهٔ معیارهای قطعی، و مقایسهٔ نتیجه با حکم اصلی.

| نتیجه | معنا | اقدام |
| --- | --- | --- |
| PASS | checkpoint معتبر است | ادامه |
| FAIL | ادعای قبلی نادرست بوده | checkpoint → `STALE`، هشدار، بررسی انسانی |
| `cannot_reproduce` (محیط drift) | اعتبار قابل اثبات نیست | `STALE` + نیاز به محیط تازه |

`STALE` هیچ‌گاه حذف نمی‌شود؛ فقط زنجیره از آن عبور نمی‌کند.

## 4. ابطال و کهنگی

چه چیزی checkpoint را باطل می‌کند؟

- تغییر `baseline_hash` (آزمون پذیرش) → باطل + نیازمند تأیید انسانی.
- تغییر کد روی شاخهٔ معتبر بدون عبور از گیت → باطل و حادثهٔ امنیتی.
- drift محیط → `STALE` (نه باطل).
- تغییر سیاست → معتبر می‌ماند؛ `policy_hash` تفاوت را نشان می‌دهد.

ابطال هرگز با حذف انجام نمی‌شود؛ با رکورد `invalidated_by` و دلیل.

## 5. بازیابی پس از قطع ناگهانی

این بخش جایی است که اکثر سیستم‌ها ادعا می‌کنند و عمل نمی‌کنند. الگوریتم صریح:

1. **بارگذاری**: آخرین `checkpoint` معتبر (زنجیره تا اولین `STALE`).
2. **پیمایش journal**: همهٔ رکوردهای پس از آن checkpoint.
3. **تشخیص رکوردهای ناتمام**: رکورد `intent` بدون `outcome` (I8).
4. **طبقه‌بندی**:
   - فراخوانی `read_only` → تکرار آزاد.
   - فراخوانی `idempotent` → تکرار با همان `idempotency_key`.
   - فراخوانی `non_idempotent` یا `unknown` → **متوقف** و ارجاع به انسان. حدس نزن که انجام شد یا نه.
5. **بازسازی lease**: lease منقضی‌شده آزاد می‌شود؛ lease زنده با `fencing_token` جدید تمدید
   نمی‌شود و کار قبلی معلق می‌ماند.
6. **ادامه**: از وضعیت وظیفهٔ معلق با `attempt_epoch` جدید.

اصل: **ادامه، تکرار کورکورانه نیست.** عملیات هزینه‌دار یا غیرقابل‌بازگشتِ نامعلوم، انسان می‌خواهد.

## 6. هم‌زمانی

- یک lease به‌ازای هر worktree (I9)، با `owner`, `expires_at`, `fencing_token`.
- هر نوشتن باید آخرین `fencing_token` را ارائه دهد؛ توکن قدیمی = رد.
- کار موازی فقط در worktreeهای جدا، و ادغام آن‌ها خودش یک وظیفهٔ مستقل با معیار پذیرش است —
  نه یک merge خودکار.
- SQLite در حالت WAL، تراکنش‌های کوتاه، `busy_timeout` مشخص.

## 7. rollback

`rollback` = بازگشت شاخهٔ کاری به `parent` checkpoint و بسته‌شدن وظیفهٔ فعلی با وضعیت `FAILED`.
شواهد و journal پاک نمی‌شوند؛ تاریخ شکست خودش داده است.

`rollback_on_failed_validation: true` یعنی پس از `max_patch_attempts` بدون PASS، کار به‌طور خودکار
به آخرین checkpoint برمی‌گردد — اما وظیفه بسته نمی‌شود، به `AWAITING_HUMAN` می‌رود.

## 8. سؤال‌های باز

- آیا یک پروژه می‌تواند بیش از یک زنجیرهٔ معتبر داشته باشد (مثلاً شاخهٔ نگهداری)؟ پیشنهاد نسخهٔ
  ۱: نه. یک زنجیره، ساده و قابل حسابرسی.
- نقطهٔ ادغام کار موازی: چه کسی تعیین می‌کند کدام worktree برنده است؟ پیشنهاد: انسان، در
  اولین نسخه؛ خودکارسازی ادغام، ریسک بی‌جهت است.
