# قرارداد ۶ — شکست و بازیابی

نسخه: 0.1 · وابسته به: [20-tool](20-tool.md), [40-evidence](40-evidence.md), [50-checkpoint](50-checkpoint.md)

هدف این سند حذف ابهام در لحظهٔ خرابی است. برای هر کلاس شکست باید از پیش معلوم باشد: چه کسی
تشخیص می‌دهد، چه کسی تصمیم می‌گیرد، چه بودجه‌ای مصرف می‌شود، و آیا تلاش مجدد مجاز است.

---

## 1. طبقه‌بندی شکست

| کلاس | نمونه | تشخیص‌دهنده | واکنش پیش‌فرض | مصرف بودجه |
| --- | --- | --- | --- | --- |
| `transient` | timeout شبکه، 429، قطع اتصال | Model/Tool Gateway | تلاش مجدد با backoff (محدود) | بودجهٔ فنی (نه اصلاح) |
| `policy_denied` | ابزار غیرمجاز | Policy Engine | توقف فوری، ارجاع به انسان | صفر |
| `bad_input` | آرگومان نامعتبر | schema | اصلاح ورودی توسط عامل | یک تلاش |
| `environment` | وابستگی نیست، نسخهٔ پایتون غلط | harness | توقف، نیازمند اقدام انسانی | صفر |
| `product_bug` | آزمون شکست، lint خطا | Verifier | تشخیص → اصلاح → بازآزمون | بودجهٔ اصلاح |
| `spec_ambiguity` | نیازمندی ناقص | Planner/عامل | توقف، `BLOCKED_ON_AMBIGUITY` | صفر |
| `test_defect` | خود آزمون غلط است | بازبینی شواهد/انسان | توقف؛ تغییر baseline نیازمند تأیید | صفر (اصلاح آزمون با انسان) |
| `budget_exhausted` | سقف پول/زمان/تلاش | Budget Manager | توقف تمیز + گزارش | — |
| `sandbox_violation` | تلاش نوشتن بیرون از محدوده | Sandbox | توقف، **قرنطینه** | — |
| `tamper_suspected` | تغییر baseline/سیاست/شواهد | Verifier | توقف، قرنطینه، گزارش | — |
| `unknown` | هر چیز دیگر | — | توقف؛ پیش‌فرض fail-closed | — |

نکتهٔ کلیدی: فقط `transient` و `product_bug` حق «تلاش مجدد» دارند. بقیه توقف‌اند.

## 2. تفکیک دو نوع retry که نباید قاطی شوند

| | retry فنی | retry اصلاح |
| --- | --- | --- |
| برای چه | خطای موقت ارتباطی | کد اشتباه است |
| چه کسی | Gateway، خودکار | عامل، با طرح جدید |
| بودجه | `max_retries` فنی | `max_patch_attempts` مهندسی |
| شاهد لازم | خیر | `diagnosis` اجباری |
| اثر | نامرئی در تاریخ مهندسی | ثبت‌شده به‌عنوان تلاش |

اگر این دو یکی شوند، یک قطعی شبکه ممکن است سه «اصلاح» بی‌معنا مصرف کند و بودجه را بسوزاند.

## 3. اثر انگشت شکست تکراری

```
failure_fingerprint = hash(
    normalized_error_signature,   # پیام خطا با حذف مسیرها/آدرس‌های متغیر
    failing_criterion_id,
    file_set_hash                 # مجموعهٔ فایل‌های درگیر
)
```

قواعد:

- همان اثر انگشت **دو بار** → تلاش سوم مجاز نیست.
- تلاش دوم فقط اگر `diagnosis` جدید ریشهٔ متفاوتی پیشنهاد کند.
- تلاش سوم → `BLOCKED` و ارجاع به انسان، همراه با هر سه گزارش تلاش.

این قاعده بیشترین پول را نجات می‌دهد: حلقه‌های «همان اصلاح، همان شکست» گران‌ترین الگوی خرابی‌اند.

## 4. توقف و قرنطینه

**توقف تمیز** (`BUDGET_EXHAUSTED`, `environment`): وظیفه به `AWAITING_HUMAN` می‌رود، worktree
دست‌نخورده می‌ماند، شواهد بسته می‌شوند، گزارش ساخته می‌شود.

**قرنطینه** (`sandbox_violation`, `tamper_suspected`): فوری، بدون تلاش مجدد:

1. متوقف‌کردن کار و ابطال lease.
2. منجمدکردن worktree برای بررسی (بدون حذف).
3. ثبت رکورد حادثه با شواهد.
4. ممنوع‌کردن ادامهٔ خودکار برای آن وظیفه.
5. اعلام به انسان — و **بدون** تفسیر خودکار در ادامه، تا وقتی انسان تصمیم بگیرد.

قرنطینه قابل «رد کردن» توسط عامل نیست. اگر چنین مسیری وجود داشته باشد، طراحی شکست خورده است.

## 5. شکست‌هایی که فوراً کل اجرا را متوقف می‌کنند

- نقض `immutable_paths`
- تلاش برای تغییر baseline یا سیاست
- ناسازگاری `content_hash` شواهد
- checkpoint بدون مجوز Verifier
- تلاش مدل برای اجرای دستور از داخل محتوای مخزن (I7)

اینگونه موارد `HALTED_FOR_SECURITY` هستند، نه `FAILED`. اصل: شکست امنیتی، شکست وظیفه نیست.

## 6. حالت `BLOCKED_ON_AMBIGUITY`

شکلی از شکست که نباید کورکورانه تلاش مجدد کند و نباید حدس بزند:

```yaml
block:
  kind: ambiguity
  question: "منظور از «امن» کدام استاندارد است: bcrypt با هزینهٔ ۱۲ یا Argon2id؟"
  options: ["bcrypt", "argon2id", "تصمیم انسانی"]
  blocking_decision: "hash algorithm"
  why_it_matters: "تغییر آن بعد از پیاده‌سازی، مهاجرت داده لازم دارد"
  guessed: false
```

قواعد: `guessed` همیشه `false`؛ حدس ممنوع (I12). پاسخ انسان به این پرسش، یک `human_approval`
می‌سازد که به تصمیم گره می‌خورد.

## 7. گزارش پس از شکست (حداقل محتوا)

- خلاصهٔ یک‌خطی شکست و کلاس آن.
- اثر انگشت شکست‌ها و تعداد تلاش.
- فهرست شواهد جمع‌شده و آنچه مفقود مانده.
- هزینهٔ مصرف‌شده از هر سقف.
- آخرین checkpoint معتبر.
- تصمیم پیشنهادی: ادامه با ورودی انسانی، تفکیک وظیفه، یا کنارگذاری.

گزارشِ «ناموفق بود» بدون این‌ها، گزارش نیست.

## 8. سؤال‌های باز

- تعداد مجاز `transient` قبل از اینکه خودش یک شکست شود؟ (پیشنهاد: ۴ با backoff نمایی.)
- آیا `test_defect` می‌تواند بدون انسان حل شود؟ (پیشنهاد: نه. خودآزمون‌سازی آزمون‌ها همان
  بازی است که می‌خواهیم از آن فرار کنیم.)
