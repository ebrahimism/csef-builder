# بازبینی جداگانهٔ T007

وضعیت نهایی: **approve برای بستن برش محدود T007 با هش منبع و رسید کامل زیر؛ مانع بازبینی باقی نمانده است.**

این مرور در همان نشست جداگانهٔ بازبین مراحل قبل انجام شده است. کد محصول و
تست‌ها در این نشست تغییر نکرده‌اند و pytest، تماس مدل، API یا سرویس پولی تازه‌ای
اجرا یا فعال نشده است. این گزارش مجوز انتشار نیست.

## دامنه و روش

پذیرش T007، یادداشت طراحی، Workflow، stages/handoffs، اتصال CLI و __main__،
استخراج Gate._verified_in و callback داخلی Book.finish، راهنمای WORKFLOW و
آزمون integration/test_chat_to_handoff.py خوانده شدند. تمرکز بر مرز اختیار
تحویل، حفظ revision مالک، مصرف بایتِ snapshot معتبر و منع پیشروی از REVIEW بود.

## ارزیابی مرز اختیار

- Gate._verified_in همان مسیر مشترک accept و تحویل است: وضعیت verified، آخرین
  evaluation دارای pass، oracle جاری، hash واقعی report، قرارداد سخت‌گیرانهٔ
  VerificationRecord، tuple نسخه/hash مالک، شناسه‌های run/evaluation، منبع و
  spec، measurement_only=false، boundary verified و همهٔ caseهای دقیق oracle
  کنترل می‌شوند. manifest واقعی candidate و snapshot نیز با source_hash برابر
  باید بمانند. خروجی JSON مدل یا برچسب نقش جای این resolve را نمی‌گیرد.
- verified_bundle از snapshot همان evaluation بایت می‌خواند و hash آن را دوباره
  می‌سنجد. finalize_validator پیش از تحویل، همان eval_id/report/source/spec را
  زیر writer transaction نهایی Book.finish دوباره resolve می‌کند. این callback
  پس از آماده‌سازی blob و کنترل lease/revision و پیش از ثبت handoff اجرا می‌شود؛
  اتصال موجود را می‌گیرد و میان resolve نهایی و ثبت تحویل transaction تازه‌ای
  باز نمی‌شود. پیشنهاد کد یا تغییر مالک در فاصلهٔ آماده‌سازی blob تا تحویل باید
  fail-closed شود؛ هر دو مسیر در regression موجودند.
- ArtifactStore.put بیرون writer transaction نهایی می‌ماند. callback یک عملیات
  داخلی controller است و permit قابل‌انتقال به مدل تولید نمی‌کند. engine هیچ
  checkpoint درج نمی‌کند؛ release_approved همواره false است.
- prior_sources فقط handoff دارای check کنترل‌کنندهٔ INDEPENDENT_GATE/passed
  را مصرف می‌کند و بایت source را با hash ثبت‌شده می‌سنجد. نام‌گذاری سندِ مدل به
  verification.json یا source/app.py، آن سند را به تحویل کد معتبر تبدیل نمی‌کند.
  regression مثبتِ هفت‌مرحله‌ای همین spoof را دارد؛ agent.calls==1 نشان می‌دهد
  برنامهٔ درستِ داخل سند مصرف نشده و کد واقعاً از مسیر عامل تولید شده است.
- handoff تاریخیِ معتبر، بایت تاریخیِ مشخصی است؛ تغییر بعدی candidate آن بایت را
  بازنویسی نمی‌کند. مصرف این خروجی checkpoint انتشار تازه نیست. این کنترل‌ها
  جای مرز سیستم‌عامل یا مقاومت در برابر نویسندهٔ دلخواه control DB را نمی‌گیرند.

## رفتار و یافتهٔ اصلاح‌شده

سؤال معتبر پیش از تماس provider برمی‌گردد. نیاز به reviewer پیش از تولید سندِ
معماری/قرارداد کنترل می‌شود؛ needs_owner سؤال پایدار می‌سازد، known question
تکراری بدون سؤال تازه به needs_revision می‌رود و needs_revision یا مدارک دارای
issue مرحلهٔ وابسته را جلو نمی‌برد. تغییر owner، مدارک قبلی را نیز باطل می‌کند.
بودجهٔ تماس قبل از تماس عامل رزرو می‌شود و خطای دارای نتیجهٔ نامعلوم lease را
برای بازیابی صریح نگه می‌دارد؛ retry خودکارِ اثر نامعلوم وعده داده نشده است.

یافتهٔ محدودِ ناسازگاری اندازه بسته شد: document_artifacts و Book.finish تا
۱ مگابایت می‌پذیرفتند، اما بازخوانی پایان workflow از file_bytes با سقف ۲۵۶
کیلوبایت استفاده می‌کرد. next_stage اکنون path معتبر، فایل عادی، حد ۱ مگابایت
قبل و پس از read و hash را کنترل می‌کند؛ source اجرایی همچنان حد ۲۵۶ کیلوبایت
خودش را دارد. regression مثبت سند ۲۶۰ کیلوبایتی دارد و پایان workflow باید
آن را بپذیرد. این یافته موجب پذیرش جعلی نمی‌شد، اما پایان معتبر را رد می‌کرد.

## حدود پذیرش معنایی

این برش یک مسیر مشترکِ قابل‌اجرا از intake و اسناد تا کد و تحویل است، با شش تا
۲۴ مرحله. قرارداد جایگاه‌ها صریح است: سه جایگاه نخست سند و بقیه برش اجرایی‌اند؛
همهٔ برش‌های اجرایی یک oracle ازپیش‌نوشته و منجمد را به کار می‌برند. این نتیجه
اثبات اجرای معنایی هر نقش دلخواه یا تولید خودکار معیار کافی از گفتگو نیست.

کنترل مکانیکی سند فقط مسیر/اندازه/غیرتهی‌بودن، حضور شناسه‌های fact و نبود issue
اعلام‌شده است؛ حضور ID اثبات رعایت معنایی نیاز نیست. reviewer معماری/قرارداد
یک بررسی مدل جدا دارد، اما مرجع صدور PASS مستقل یا احراز هویت مالک نیست.
source_ref توصیفی و API مالک متعلق به controller مورد اعتماد باقی می‌مانند.

آزمون مثبت، پاسخ‌های مدل scripted و probe اجرایی TEST DOUBLE صریح دارد؛ خود
برنامهٔ Python واقعاً با subprocess اجرا می‌شود. عبور آن اثبات موفقیت مدل زنده
یا ایزولاسیون میزبان نیست. measure-only ویندوز REVIEW می‌ماند، check تحویل false
است، مرحلهٔ وابسته متوقف می‌شود و Gate.accept نیز آن را نمی‌پذیرد.
