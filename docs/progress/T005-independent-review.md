# بازبینی جداگانهٔ T005

وضعیت نهایی: **approve برای بستن برش محدود T005 با هش منبع و رسید کامل ثبت‌شده؛ مانع بازبینی باقی نمانده است.**

این مرور هدفمند در همان نشست جداگانهٔ بازبین T003/T004 انجام شده است. کد محصول،
تست‌ها، اسناد هدف و backlog در این نشست تغییر نکرده‌اند. آزمون tracker، مدل، API
یا سرویس پولی تازه‌ای فراخوانی نشده است. این گزارش مجوز انتشار نیست.

## دامنه و روش

پذیرش T005 و نیازهای REQ-104/REQ-106، سه سرویس lifecycle، refactor مسیر owner در
ProjectBook، قرارداد VerificationRecord و مسیر آغاز/ثبت/پذیرش Gate خوانده شدند.
آزمون‌های fact authority و اصلاحات پس از یافته‌ها نیز بازخوانی شدند. تمرکز این
بررسی حفظ هدف، منشأ واقعی در سطح کنترل‌کننده، تازگی نسخه، مصرف یک‌بارهٔ گفتهٔ
صاحب پروژه، تاریخچهٔ superseded و آثار اتمیک تغییر است.

## یافته‌ها و اصلاحات بررسی‌شده

۱. اجباری‌بودن پارامتر expected_version کافی نبود؛ مقدار None می‌توانست بررسی
نسخه را دور بزند. اکنون هر سه API صاحب پروژه پیش از SQL، عدد صحیح مثبتِ غیرbool
می‌خواهند؛ None، float و string پذیرفته نمی‌شوند.

۲. تاریخچه نباید body نسخهٔ قدیمی یا اشارهٔ منشأ را بدون کنترل بازگرداند.
`_timeline` اکنون یک snapshot خواندن می‌گیرد؛ shape و hash هر revision، پیوند
from/to و before/after، یکتایی audit هر نسخه و delta واقعی fact را بررسی می‌کند.
آثار goal و answer از دو revision بازسازی می‌شوند و ادعای audit باید دقیقاً
همان باشد. ref منشأِ owner باید به owner_consumed موجود با نسخه/hash پایهٔ
متناظر اشاره کند؛ برای پیشنهاد پذیرفته‌شده، ردیف accepted و target hash گفتهٔ
owner نیز کنترل می‌شوند. خرابی این پیوندها به تاریخچهٔ ظاهراً معتبر تبدیل نمی‌شود.

۳. staleکردن pass فعلی به‌تنهایی کافی نبود؛ اجرای ارزیاب می‌توانست پس از تغییر
owner نتیجهٔ قدیمی را pass کند. Gate اکنون در آغاز و پایان ارزیابی و هنگام accept
در transaction نویسنده، جفت version و SHA هدف را کنترل می‌کند. تغییر حین اجرا
نتیجه را blocked می‌کند. hash محتوا به‌تنهایی برای no-op revision یا A→B→A کافی
نیست؛ project_version سخت‌گیرانه کنار آن بسته شده است. قرارداد هر دو فیلد را با
هم می‌خواهد؛ Gate-only/legacy با جفت None سازگار می‌ماند. تاریخچهٔ accepted قبلی
بازنویسی نمی‌شود و به اختیار تازه تبدیل نمی‌گردد.

## ارزیابی معنایی

- مسیر مدل همیشه status=proposed می‌نویسد. برچسب owner یا approved در JSON مدل
  به ردیف جداگانهٔ owner_recorded تبدیل نمی‌شود. فرض نیز خودکار fact پذیرفته نیست.
- گفتهٔ owner به نسخه/hash فعلی و تغییر مستقیم مشخص یا بایت دقیق یک پیشنهاد
  مشخص گره می‌خورد. گفتهٔ بدون هدف مشخص، اجازهٔ عمومی نمی‌سازد. تغییر پیشنهاد،
  تغییر هدف پذیرش، نسخهٔ کهنه و مصرف دوباره رد می‌شوند.
- پذیرش پیشنهاد، ایجاد revision و audit، statusهای accepted/owner_consumed،
  staleکردن مراحل، fencing lease و لغو passهای پذیرفته‌نشده در یک transaction
  انجام می‌شوند. رقابت دو کنترل‌کننده نمی‌تواند دو نسخه از یک گفته بسازد.
- شناسه‌های fact باقی می‌مانند، متن قبلی در revisionهای پیشین نگهداری می‌شود و
  history آن را superseded نشان می‌دهد. تصمیم تازه به‌صورت fact دارای شناسهٔ ADR
  ثبت می‌شود؛ نوع fact پذیرفته‌شده بی‌صدا تغییر نمی‌کند. برای دادهٔ قدیمیِ فاقد
  منشأ، legacy_unattributed گزارش می‌شود و هویت صاحب پروژه جعل نمی‌شود.
- revision_history آثار و اشاره‌های منشأ را در API می‌دهد؛ UI برای بازسازی این
  اطلاعات به خواندن مستقیم SQL نیاز ندارد.

## حدود اعتبار

ثبت owner_statement تنها برای مسیر گفت‌وگوی مورد اعتماد/کنترل‌کننده است؛ این
تفکیک، مرز دسترسی سیستم‌عامل یا احراز هویت مستقل انسان نیست. source_ref پیشنهاد
مدل یک اشارهٔ توصیفی است و به‌تنهایی رسید معتبر Harness یا اثبات وقوع model call
محسوب نمی‌شود. hash/نسخه جلوی تغییر بی‌صدای داده در API بررسی‌شده را می‌گیرند،
اما دفاع در برابر نویسندهٔ مستقیم DB را تضمین نمی‌کنند.

ابطال محافظه‌کارانهٔ مرحله و تازگی Gate، صحت معنایی تبدیل هدف جدید به معیارهای
آزمون را ثابت نمی‌کند. accepted قدیمی سابقهٔ همان مشاهده است؛ مجوز اجرای هدف
تغییریافته یا انتشار جدید نیست. محدودیت loopback ویندوز و REVIEW در measure-only
تغییر نکرده‌اند. کاهش هزینه، امنیت عمومی و موفقیت پروژهٔ پیشرفته از این مرور
نتیجه نمی‌شوند.

`T005-focused-check.json` با شناسهٔ `38b7171626b047c0a7da2f5430229963`، ۱۸ موفق
و زمان فرایند ۱۳۲٫۵۹۴ ثانیه. هر دو خروج ۰ و صفر failure/error/skip و بدون

به منبع نهاییِ پس از آخرین صحت‌سنجی history نسبت داده نمی‌شوند.

در `2026-11-16T14:26:04+04:00` رسید کامل `T005-full-check.json` مستقیماً خوانده

و زمان فرایند کنترل‌شده ۵۲۸٫۰۷۸ ثانیه است. JUnit واقعی همان اجرا در
`.csef-build/checks/0fe239f632dc44bc93da135e90965d8c/junit.xml` نیز مستقیم خوانده
شد و ۲۰۹ testcase بدون failure/error/skipped داشت.

snapshot جاری با تابع خود کنترل‌کننده محاسبه شد و با source/after رسید کامل
برابر بود:
`98c9b7a984bd760aea04dbf07dba61326f88b31545a5d9fca4c15c0caba17185`.
بنابراین drift مشاهده نشد و آزمون کامل تازه‌ای اجرا نشد. چهار فایل schema نیز
با model_json_schema مدل runtime متناظر در بررسی فقط‌خواندنی برابر بودند.
گزارش تحویل محدودیت source_ref، trusted-owner API، fake آزمایشی ارزیاب و تفاوت
binding تازگی با صحت معنایی oracle را صریح نگه داشته است.

نتیجهٔ نهایی: در دامنهٔ بررسی‌شده پیشنهاد مدل یا فرض نمی‌تواند هدف/واقعیت
پذیرفته‌شده را تغییر دهد؛ تغییر owner به ورودی مشخص و نسخهٔ دقیق بسته و یک‌بار
مصرف می‌شود؛ تاریخچه و آثار با revisionهای واقعی کنترل می‌شوند؛ stale/concurrent
و نتیجهٔ ارزیابی پیش از revision تازه، حتی با متن یکسان، اختیار پذیرش جدید
نمی‌سازند. بستن T005 برای همین هش منبع تأیید می‌شود. این تأیید، احراز هویت انسان،
دفاع در برابر نویسندهٔ مستقیم DB، کیفیت عمومی پروژه یا مجوز انتشار نیست.
