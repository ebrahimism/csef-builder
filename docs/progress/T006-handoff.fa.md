# T006 — پرسش پایدار و پاسخ قابل ویرایش

این برش به همان مسیر assist، ProjectBook و پروتکل گفتهٔ صاحب پروژه متصل است.
پرسش با دلیل ضرورت، اثر تصمیم، منبع توصیفی، نسخهٔ پایه، شناسه‌های نیاز/تصمیم مرتبط
و hash زمینه ثبت می‌شود. نبود fact_ids یعنی پرسش در سطح هدف؛ شناسهٔ ناموجود
پذیرفته نمی‌شود. حداکثر سه سؤال در نوبت و توقف مدل تا پاسخ حفظ شده است.

کلید یا متن یکسان‌شده، مرحله و پیوند نیازها، سؤال را در همان زمینه پایدار می‌کنند.
پرسش قبلاً پاسخ‌داده‌شده در همان زمینه دوباره pending نمی‌شود. تغییر نیاز مرتبط
یا هدف، زمینهٔ تازه می‌سازد؛ تغییر نیاز نامرتبط، پاسخ معلوم را نامعلوم نمی‌کند. یک کلید
برای متن واقعاً متفاوت به‌جای حدس‌زدن معنای سؤال رد می‌شود. این کنترل مکانیکی
است، نه تضمین فهم همهٔ بازنویسی‌ها یا ابهام‌های معنایی توسط مدل.

API پاسخ، نسخهٔ integer دقیق می‌خواهد. گفتهٔ کاربر به hash تغییر مشخص answers
و fact_updates صریح متصل و یک‌بار مصرف می‌شود. پرسش پاسخ‌داده‌شده قابل ویرایش است؛
پرسش اصلی حذف یا بازنویسی نمی‌شود. مشاهدهٔ هر پاسخ همراه نسخه، hash، منبع و
پیوند نیاز در همان تراکنش تغییر owner ثبت می‌شود، حتی اگر پاسخ عیناً تکرار شده باشد.
تاریخچهٔ قدیمی باقی می‌ماند و نسخهٔ منسوخ از آخرین پاسخ جدا دیده می‌شود. خواندن
history، نسخه‌ها، audit و مشاهدات پاسخ را از یک snapshot سازگار بررسی می‌کند.

سؤال pending که زمینه‌اش عوض شده حفظ می‌شود اما در سؤال‌های فعال نمایش داده
نمی‌شود و مدل را بی‌دلیل متوقف نمی‌کند. پاسخ به آن، چه در API جدید چه در مسیر
قدیمی amend، داخل همان writer transaction نسبت به body پیش از تغییر رد می‌شود.
سؤال تازه شناسهٔ تازه دارد. ویرایش پاسخِ معتبر می‌تواند fact مرتبط را صریحاً تغییر
دهد؛ observation نسبت به body پس از تغییر ثبت می‌شود. observation تکراری برای
یک سؤال/نسخه خطای integrity است. intake با ساختار معتبر Answer نیز معلوم است.

پاسخ خام خودکار به تغییر متن نیاز تفسیر نمی‌شود. فقط fact_updates صریح و فقط برای
شناسه‌های مرتبط اجازه دارد؛ هدف یا تصمیم نامرتبط از روی پاسخ تغییر نمی‌کند. ورودی
قدیمی، پیوند نامعتبر و history خراب رد می‌شوند. دادهٔ قدیمیِ بدون مشاهدهٔ پاسخ
از revision واقعی بازیابی و با منبع ثبت‌نشدهٔ صریح نمایش داده می‌شود؛ منشأ ساخته نمی‌شود.

assist پس از ثبت سؤال از همین سرویس استفاده می‌کند. تا pending باقی است بدون
تماس تازه با provider برمی‌گردد. اگر مدل همان سؤال معلوم را تکرار کند، خروجی آن
به انتظار بی‌پاسخ جعلی تبدیل نمی‌شود؛ پیش‌نویس همچنان نیازمند اعتبارسنجی است.
schema خروجی نقش fact_ids را لازم دارد؛ پاسخ قدیمیِ adapter بدون آن با scope هدف
پشتیبانی می‌شود. هیچ تماس مدل زنده یا API پولی برای این تغییر اجرا نشده است.

آزمون متمرکز ۲۶ مورد موفق داشت: ویرایش و پیوند نیاز، حفظ تصمیم نامرتبط، dedupe
وابسته به زمینه، جلوگیری از provider call تا پاسخ، رقابت دو ثبت سؤال، ویرایش intake،
منع حدس تغییر نیاز، stale/ابهام کلید و دستکاری مشاهدهٔ پاسخ. پس از آن خواندن
تاریخچه در یک snapshot واحد قرار گرفت و دستور مدل برای پیوند شناسهٔ واقعی روشن شد.
رسید کامل منبع نهایی و مرور ثبت‌شده شرط اتمام هستند؛ نتیجهٔ متمرکز جای آن‌ها نیست.

اجرای کامل میانی 72485f37cf52448b9b23d5ba301ab4ea پس از اعلام یافته‌های بازبین
عمداً متوقف شد تا اصلاحات یک‌جا آزموده شوند. رسید interrupted نگه داشته شده:
exit 4294967295، نبود JUnit کامل، passed=false؛ این شکست محصول یا شاهد اتمام
محسوب نشده است. آزمون‌های افزوده drift در pending/answered، تغییر goal، observation
تکراری، intake ساختاری و snapshot هم‌زمان واقعی با writer مستقل را پوشش می‌دهند.

حدود: auth انسانی و ایزولاسیون OS اضافه نشده‌اند؛ ورودی owner از controller معتمد
می‌آید. source_ref رسید Harness نیست. freshness/پیوند مکانیکی، صحت معنایی سؤال
یا oracle را اثبات نمی‌کند. بازنگری معنایی و کنترل‌کنندهٔ عمومی در مراحل بعد ادامه
دارند. Gate مستقل و REVIEW بودن measure-only ویندوز تغییر نکرده‌اند.

بازبینی اصلاحات با ۵۵ آزمون متمرکز موفق بود (رسید db91e8e5db3f4dfe9bd49739aee1201c).
پس از این رسید، چهار پاسخ اصلی intake هم به زمینهٔ عمومی اضافه شدند؛ ساختار
Answer و string با اطلاعات پاسخ یکسان، زمینهٔ یکسان دارند. پاسخ به Q نامرتبط
زمینهٔ سؤال دیگر را تغییر نمی‌دهد. این تغییر و مسیر واقعی CLI در آزمون کامل
نهایی سنجیده می‌شوند، نه با انتساب رسید قبلی به منبع تازه.

فرمان project answer اکنون از همین سرویس owner استفاده می‌کند؛ --version نسخهٔ
صریح مورد انتظار و --fact ID TEXT تغییر صریحِ نیاز مرتبط است. ویرایش پاسخ و نیاز
با حفظ تاریخچه انجام می‌شود و فرمان نسخهٔ قدیمی را رد می‌کند. نبود --version یعنی
نسخهٔ جاری هنگام دریافت فرمان، برای سازگاری با روش قدیمی؛ سؤال اصلی حفظ می‌شود.
