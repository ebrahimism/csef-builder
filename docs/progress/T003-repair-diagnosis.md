# تشخیص و سابقهٔ اصلاح T003

نخستین بررسی متمرکز کنترل‌کننده، رسید `b3a82ef1dc8f481d8be971477b8ce6cf`،
۸۱ مورد را اجرا کرد: ۷۱ موفق و ۱۰ ناموفق، بدون skip/error. هش منبع قبل و بعد یکسان
بود؛ شکست‌ها واقعی بودند، نه تغییر هم‌زمان منبع. رسید خام در
`T003-focused-attempt1.json` حفظ شده است.

دو علت مشترک در شکست‌های انتقال دیده شد:

۱. `unlink` قفل publication پیش از بستن handle روی Windows خطای ۳۲ می‌داد.
همچنین context manager اتصال sqlite به‌تنهایی connection را close نمی‌کند.
بستن صریح lock و اتصال initialize/reference/backup به کد اضافه شد. fixtureهایی که
DB فایل‌دار باز می‌کردند نیز اتصالشان را صریح می‌بندند.

۲. نام staging طولانی، همراه مسیر backup و run/evaluation، محدودیت مسیر Windows
را رد می‌کرد و خطای ۲۰۶ می‌داد. نام staging کوتاه شد و preflight برای مسیر مقصد
غیرقابل پشتیبانی، پیش از نوشتن داده، خطای روشن می‌دهد. هیچ تنظیم میزبان، registry
یا پذیرش آزمون برای رفع این شکست تغییر نکرد.

بازبینی جدا نیز نشان داد `Path.absolute()` به‌تنهایی `..` را حذف نمی‌کند و guard
جدابودن مسیر می‌تواند خطا کند. پیش از اجرای اصلاح بعدی باید مسیرهای ریشه پس از
بررسی reparse point، canonical شوند و آزمون nested destination با `..` اضافه شود.
نسخه و شکل manifest بازیابی نیز باید پیش از ساخت staging کنترل شوند.

این سند سابقهٔ تشخیص است؛ موفقیت نهایی فقط در رسید جاری و گزارش پذیرش ثبت می‌شود.
