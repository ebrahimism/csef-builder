# یادداشت آماده‌سازی T007

این یادداشت وضعیت اتمام نیست؛ T006 باید نخست با رسید جاری بسته شود. نقشهٔ راه
و قراردادهای مالک ورودی ثابت می‌مانند. هدف، اتصال کدهای کارکرده است، نه چارچوب موازی.

مسیر پیشنهادی: پروندهٔ پروژه و پاسخ‌های نسخه‌دار ← اولین مرحلهٔ آماده ← دستیار
نقش مربوط ← بررسی واقعی خروجی ← تحویل ثبت‌شده. سؤال باز معتبر پیش از هر تماس
مدل برمی‌گردد. شش مرحلهٔ پیش‌فرض حفظ و تعریف تعداد بیشتر پشتیبانی می‌شود.

برای مدارک، بررسی ساختار، غیرخالی‌بودن و ارجاع شناسه‌ها مکانیکی است؛ بررسی
معنایی معماری/قرارداد از نشست reviewer می‌آید و به‌تنهایی اختیار Gate نیست.
خروجی needs_owner باید سؤال پایدار بسازد؛ needs_revision یا مدرک ناقص، تحویل
ready نمی‌سازد. مدل هیچ check پذیرفته‌ای تولید نمی‌کند.

برای کد، همان Gate با oracle منجمد و مخزن مشترک به کار می‌رود. نسخهٔ کد قبلیِ
معتبر مبنای مرحلهٔ وابسته است. report/source/spec/revision پیش از تحویل دوباره
سنجیده می‌شوند؛ فقط خروجی ثبت‌شدهٔ معتبر مصرف می‌شود. controller عمومی در این
برش checkpoint انتشار صادر نمی‌کند. REVIEW، از جمله measure-only ویندوز، مرحلهٔ
وابسته را پیش نمی‌برد. اجرای واقعی محلی با REVIEW هم باید صریحاً از عبور موفق
شاخه‌های کنترل در fixture مورد اعتماد جدا گزارش شود.

API عمومی مرحله را بدون دستکاری SQL اجرا می‌کند. CLI به همان API وصل می‌شود.
آزمون end-to-end باید با گفتگوی نمونه، مدارک، پیشنهاد اصلاح کد و اجرای واقعی
برنامهٔ ثابت توسط subprocess پیش برود؛ ورودی provider در آزمون scripted است و
نباید به‌عنوان موفقیت مدل زنده یا ایزولاسیون واقعی معرفی شود. آزمون‌های منفی،
artifact خراب، review مردود، owner revision عوض‌شده و REVIEW را متوقف می‌کنند.

تلاش مدل قبل از تماس در بودجهٔ پایدار ثبت می‌شود. خطا/قطع نامعلوم lease را
آزاد نمی‌کند؛ تکرار خودکار اثر خارجی جای بازیابی صریح نیست. این یادداشت نیازمند
بازخوانی قرارداد و پیاده‌سازی پس از آغاز T007 در tracker است.
