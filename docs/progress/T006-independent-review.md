# بازبینی جداگانهٔ T006

وضعیت نهایی: **approve برای بستن برش محدود T006 با هش منبع و رسید کامل ثبت‌شده؛ مانع بازبینی باقی نمانده است.**

این مرور در همان نشست جداگانهٔ بازبین مراحل قبل ادامه دارد. کد محصول و تست‌ها
در این نشست تغییر نکرده‌اند؛ pytest، مدل، API یا سرویس پولی تازه‌ای اجرا یا فعال
نشده است. این گزارش مجوز انتشار نیست.

## دامنه و روش

پذیرش T006 و هدف‌های REQ-103/REQ-104، Questions، تغییرات ProjectService و
ProjectBook، اتصال assistant و آزمون‌های question revisions خوانده شدند.
تمرکز بر اتصال پاسخ به نیازِ دارای شناسه، حفظ نسخهٔ قدیمی، منع حدس متن نیاز،
تشخیص پاسخ معلوم در context واقعی و جلوگیری از تماس تکراری مدل تا پاسخ owner است.

## یافته‌ها و وضعیت آن‌ها

۱. answer_history در نسخهٔ نخست timeline و observationها را از snapshotهای جدا
می‌خواند؛ ویرایش هم‌زمان معتبر می‌توانست به خطای کاذب integrity تبدیل شود.
اصلاح بازخوانی شد: `_timeline(con=...)` و answer_history اتصال snapshot مشترک
می‌گیرند؛ Book.questions نیز current و ردیف‌های سؤال را در همان snapshot می‌خواند.
آزمون تازه، writer واقعی روی WAL را میان خواندن timeline و observation وارد
می‌کند و انتظار تاریخچهٔ منسجمِ نسخهٔ قبلی را دارد؛ متن آن بررسی شد.

۲. pending قدیمی پس از تغییر fact مرتبط نباید هم‌چنان assistant را مسدود کند،
یا پس از طرح سؤال تازه، دوباره به کاربر نمایش داده شود. سؤال باید حفظ شود اما
از pending فعالِ context تازه جدا باشد. هنگام answer نیز anchor باید زیر همان
writer transaction کنترل شود تا پاسخ به سؤال کهنه به نیازِ عوض‌شده نچسبد.
برای ویرایش پاسخ، آخرین observation معتبر anchor است؛ اعتبارسنجی پیش از اعمال
fact_updates و ثبت observation نسبت به body پس از تغییر انجام می‌شود. این
اصلاح در Questions.answer و نیز مسیر قدیمی Book._amend_in زیر transaction
نویسنده بازخوانی شد. سؤال قدیمی حذف نمی‌شود؛ Book.questions فقط pending دارای
anchor جاری را نمایش می‌دهد و پاسخ به anchor کهنه رد می‌شود.

۳. context سؤال دارای fact_ids، هدف کلی را در نسخهٔ نخست حذف می‌کرد. تغییر صریح
goal با factهای ثابت می‌توانست پاسخ قبلی را به‌اشتباه معلوم بشمارد. signature
باید goal و factهای منتخب واقعی را شامل شود؛ افزودن شمارهٔ revision به‌تنهایی
مناسب نیست چون تغییر نامرتبط را به تکرار بی‌دلیل سؤال تبدیل می‌کند. context_sha
اصلاح‌شده همیشه goal، چهار intake بنیادی و فقط factهای منتخب را hash می‌کند؛
تغییر ADR نامرتبط تازگی پاسخِ مربوط به REQ دیگر را بی‌دلیل از بین نمی‌برد. مقدار
answer ساخت‌یافته برای intake استخراج می‌شود، پس نمایش string و Answer با همان
اطلاعات context یکسان دارند؛ پاسخ به Q نامرتبط وارد این signature نمی‌شود.

۴. observation تکراری برای یک question_id/project_version نباید دو مدخل ظاهراً
معتبر بسازد. یکتایی آن باید هنگام خواندن تاریخچه بررسی شود؛ جدول changes این
قید دامنه‌ای را در schema ندارد. answer_history اکنون seenِ نسخه‌ها دارد و
observation تکراری را به‌عنوان خطای integrity رد می‌کند.

۵. ProjectRevision.answers مقدار str یا Answer را مجاز می‌داند. intake با Answer
معتبر و متن پاسخ غیرخالی هم باید معلوم شناخته شود؛ پذیرش این داده در قرارداد و
سپس unknownشمردن آن در Book.questions ناسازگار است. تابع known اصلاح‌شده متن
غیرخالیِ answer ساخت‌یافته را نیز معلوم می‌شمارد. ویرایش intake به نسخهٔ جاری
owner بسته است و به‌علت anchor قدیمیِ سؤال adaptive مسدود نمی‌شود.

## ارزیابی طراحی و حدود

- متن پاسخ به خودی خود متن نیاز حدس‌زده نمی‌شود. fact_updates باید صریح باشد و
  تنها شناسه‌های مرتبط با همان سؤال را تغییر دهد. تغییر ADR یا نیاز نامرتبط
  از مسیر پاسخ پذیرفته نمی‌شود.
- دادهٔ پاسخ، ویرایش بعدی، provenance، version/hash پروژه و context observation
  باید داخل transaction تغییر owner ثبت شوند. پاسخ پیشین حذف نمی‌شود و history
  آن را superseded نشان می‌دهد. گفتهٔ owner همچنان به تغییر مشخص و نسخهٔ فعلی
  بسته و یک‌بارمصرف است.
- تا وقتی pending معتبر هست، assistant پیش از client.call برمی‌گردد. تکرارِ
  همان سؤال با context یکسان و پاسخ معلوم نباید pending تازه بسازد.
- dedupe محدود به key/متن normalize‌شده و context صریح است. این بررسی، تشخیص
  معنایی همهٔ پارافریزها یا کامل‌بودن fact_ids پیشنهادی مدل را تضمین نمی‌کند.
  source_ref مدل نیز مرجع توصیفی است، نه شاهد Harness یا احراز هویت انسان.
- افزودن answers به change spec باید hash قبلیِ گفته‌های بدون answers را حفظ
  کند؛ گفتهٔ قدیمی نمی‌تواند ناخواسته اجازهٔ پاسخ تازه پیدا کند. مسیر اولیهٔ
  canonicalization غیاب/تهی‌بودن answers را به hash جدید وارد نمی‌کند و پاسخ
  غیرتهی در target hash بسته می‌شود.
- مسیر واقعی CLI نیز به Questions.answer متصل شده است. --version صریح، ورودی
  کهنه را رد می‌کند؛ غیاب آن بنا به قرارداد سازگاری، نسخهٔ جاری هنگام دریافت
  فرمان است. --fact ID TEXT فقط تغییر صریحِ fact مرتبط را می‌پذیرد و تکرار ID
  را رد می‌کند. این مسیر متن پاسخ را خودکار به نیاز تازه تبدیل نمی‌کند. تغییر
  راهنمای WORKFLOW و آزمون CLIِ ویرایش ۳۰→۹۰ روز با حفظ history بازخوانی شدند.
- مالکیت اجرای T004، جدایی proposed از owner-recorded در T005 و Gate مستقل
  باید حفظ شوند. مرز loopback ویندوز و REVIEW در measure-only تغییر نکرده‌اند.
